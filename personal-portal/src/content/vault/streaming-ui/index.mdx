# 流式生成 UI

大模型是逐 token 生成的。如果前端等整段回复攒齐再一次性渲染,用户面对的是几秒甚至十几秒的空白;而只要边到边渲,同样的等待就变成「肉眼可见的进展」。流式 UI 的价值不在炫技,而在把「等待」变成「陪伴」——这是几乎每个 LLM 前端都要处理的基础模式。

## 为什么要流式

- 首字延迟(TTFT)通常远小于整段完成时间,先把第一批字吐出来,感知速度立刻不同。
- 持续的文字增长本身就是进度反馈,不需要额外的 loading 动画去搪塞。
- 长回复可以边读边看,用户甚至能在读到一半时就判断方向对不对、要不要中断。

## 前端要解决的几件事

- **增量渲染**:每次只把新到的 chunk 追加进已有内容,而不是重排整段,避免重复布局与闪烁。
- **光标反馈**:在文本末尾放一个跳动的光标,明确「还在写」,与「已写完」区分开。
- **滚动锚定**:文字增长时自动吸到底部;但一旦用户主动上滑去回看,就不能再把他硬拽回底部——只有当他仍停在底部附近时才继续跟随。
- **可中断**:随时能停下,并保留已经生成的半截文字,而不是丢弃或回滚。
- **backpressure(背压)**:真实场景里 token 到达速率和渲染速率未必匹配,过快的 chunk 需要按帧合并或节流,否则频繁 setState 会拖垮渲染。

## 这个 demo 怎么做的

- 一个 `idle → streaming → done` 的状态机驱动三个按钮:生成、停止、重新生成,并据此禁用不合时宜的操作。
- 用递归 `setTimeout` 每 25–45ms 吐出 1–3 个字,模拟 token 陆续到达;`ref` 保存定时器与游标,停止即清定时器并保留当前文本。
- 输出框用 `ref` 记录「是否仍吸附底部」:`onScroll` 时判断距底距离,文本增长的 effect 只在吸附时才滚到底,实现不打断翻阅的滚动锚定。
- 输出区标注 `aria-live="polite"`,让屏幕阅读器平缓播报新增内容;跳动光标以 CSS 实现并 `aria-hidden`。
- 开启系统「减少动态效果」时,「生成」直接给出完整文本,不逐块、不闪光标。

## 诚实说明

这是一个**客户端模拟**的流式 demo:回复文本是预先写好的常量,由浏览器在本地按节奏吐出。它**不发起任何网络请求、不调用任何真实模型**,示范的是「接住 token 流」的前端工程手法,而非一次真实推理。选它自我指涉(内容本身讲流式 UI)也正是为了让这份诚实一目了然。
