# Together Trace — 离线优先的双人记忆地图

Together Trace 是我独立规划的一个个人项目，目标是把两个人共同走过的旅行轨迹、日常碎片和纪念时刻，沉淀进一个只属于两个人的私密空间。它面向异地情侣的使用场景，但真正想解决的问题是通用的：如何在网络不稳定、甚至没有账号的情况下，也能可靠地记录和回看共同记忆。

本文侧重技术能力的呈现，双人记忆的产品故事作为背景。文中所有结论都以项目实际代码和构建、测试结果为依据。

## 项目定位

- 这是一个个人独立规划的项目，把旅行轨迹、日常碎片和纪念时刻收拢到双人私密空间。
- 它同时提供两种使用方式：不登录时以本地模式使用，登录后进入需要双人协作的账号模式。

## 为什么采用离线优先

网络不是记录记忆的前置条件，所以数据流从一开始就按「先本地、后云端」设计：

- 无需登录也能使用本地模式，写入的内容立即可见。
- 碎片、倒计时和旅行草稿等核心数据采用本地优先策略：先写入设备存储并即时更新界面，网络恢复后再由同步队列上传，失败操作按退避策略重试。心跳、功能投票等实时协作操作仍要求在线执行，不进入离线队列。
- Android 侧的持续定位由原生前台服务承担，即使锁屏或切到后台也能继续采集轨迹。
- 需要说明的是，持续后台定位是 Android 原生能力，Web / PWA 并不具备——两者的能力边界是清晰区分的，不混为一谈。

## 核心技术结构

- 客户端是一份 React 19 + TypeScript + Vite 代码，通过 Capacitor 同时产出 Web / PWA 与 Android 应用。
- 本地数据分两层承载：Web 侧用 Dexie（IndexedDB），Android 侧的 GPS 原始轨迹点用 Kotlin / Room（SQLite）。
- 身份与成员边界由 Firebase Authentication 与 Firestore Security Rules 负责。
- 空间创建、旅行发布等敏感操作由 Cloudflare Worker 处理。
- 地图使用 Mapbox 渲染旅行路线，媒体文件存放在 Cloudflare R2；这两项都只按当前已实现的范围描述，跨旅行的「足迹地图」总览仍在规划中，不计入已完成能力。

## 工程判断

- 敏感操作（空间创建、旅行发布、心跳、旅行回声揭示）统一经过 Cloudflare Worker，由服务端校验身份并执行业务规则。
- 成员自己的内容（如日常碎片、评论、反应、投票）则允许客户端在 Firestore Security Rules 的约束下直接写入——Worker 并不是唯一的写入者，而是敏感操作的必经关卡。
- 成本上以「在免费额度内、接近零成本运行」作为设计约束来做技术选型，而不是把它当作已经核实的实际账单结论。

## 验证证据

- 项目当前可以完成完整构建，`npm run build` 通过。
- 现有自动化测试为 19 个测试文件、86 条用例，全部通过。

## 体验提示

**线上体验请使用本地模式。请勿尝试登录或录入真实私密数据。** 线上入口仅用于感受本地记录与离线交互；账号模式涉及真实的双人私密内容，不作为公开演示的一部分。
