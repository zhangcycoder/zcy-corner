# 浏览器里跑推理:能与不能

「模型在浏览器里跑」这句话,底下藏着三层不同的技术,和一条很现实的能力边界。把边界说清楚,比喊「端侧 AI」有用得多。

## 三条执行路径

- **WASM**:跑在 CPU 上,最通用。`onnxruntime-web` 有 wasm 后端,配合 SIMD 与多线程(多线程要靠 `SharedArrayBuffer`,而它需要页面开启 COOP/COEP 跨源隔离)。适合小模型、经典机器学习,或没有可用 GPU 时的兜底。缺点很实在:transformer 的大矩阵乘在 CPU 上就是慢。
- **WebGPU**:现代 GPU 的通用计算接口,是 WebGL 之后真正能做通用 compute 的一层,让「像样的 matmul 上 GPU」成为可能。Chrome 113(2023 年 5 月)起默认开启,Edge 跟进,Safari 与 Firefox 也在近版本陆续到位。端侧小 LLM 能不能用,基本就看有没有 WebGPU。
- **WebNN**:更新的 W3C 提案,目标是把推理直接下发到系统的原生加速器(NPU / GPU,经 DirectML、Core ML 之类后端)。方向很诱人,但目前仍偏实验、多数环境要开 flag——它是「未来」,还不是「现在就能稳发」。

## 量化:把模型塞进浏览器

把权重从 fp16 / fp32 降到 int8、甚至 int4,体积和显存带宽 2–4 倍地往下掉,推理更快,而精度只损失一点。

这不是可选项,而是前提:一个多 GB 的模型不量化,根本进不了浏览器的内存预算。端侧小 LLM 普遍走 int4(GGUF / GPTQ / AWQ 一类思路),就是为了在「能装下」和「还能用」之间找平衡。

## 现实的三堵墙

- **下载体积**:一个 7B 的 int4 模型 ~4GB。首次冷启动要把它整个下下来,必须靠 Cache Storage / OPFS 缓存,否则每次进页面都重下一遍。
- **内存**:浏览器标签页的内存有上限,移动端尤其紧;WASM32 的地址空间历史上卡在 ~4GB(memory64 才刚起步)。
- **延迟**:纯 CPU(WASM)跑 transformer,token/s 常低到不可用;要拿到能接受的吞吐,基本得靠 WebGPU。

## 为什么还是值得

- **隐私**:数据不出设备。敏感输入、端侧检索、离线可用——这些是云端给不了的。
- **成本**:没有按 token 计费。嵌入、分类这类高频小任务,在端侧几乎是零边际成本。

## 生态(是事实,不代表这里用了)

`transformers.js`(Hugging Face / Xenova)、`onnxruntime-web`(微软)、WebLLM(MLC,走 WebGPU + 编译后的算子)是这个方向的主力库。

但要说清楚:它们是「生态」,不等于本站用了。隔壁那件 [浏览器里的神经网络](/vault/neural-net) 是手写反向传播、零依赖,不靠上面任何一个库——它是为了把原理摊开看,不是为了跑大模型。区分「生态里有什么」和「这个页面用了什么」,是诚实叙述的一部分。

## 老实的结论:今天能与不能

**能,而且顺**:嵌入(MiniLM 一类)、小分类器 / 情感 / NER、经典机器学习(kNN、决策树、小 MLP)、小图像模型;以及在有 WebGPU 时的小 LLM(1–3B,如 Phi-mini、Qwen 0.5–1.5B、Llama-3.2-1B,配 int4)。

**难,会疼**:7B 以上(下载、内存、冷启动三堵墙叠加)、对延迟敏感却只有 CPU 的场景、以及没有 WebGPU 的老环境。

> 端侧推理不是「能不能跑起来」的是非题,而是「跑什么、在什么设备、用户愿不愿意等这次下载」的工程题。选对模型尺寸,往往比选对框架重要得多。
